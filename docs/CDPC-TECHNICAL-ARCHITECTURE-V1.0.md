# CDPC 总体技术架构与开发规范 V1.0

> 项目：CDPC（Pixcape）
> 版本：V1.0
> 制定日期：2026-11-07
> 状态：架构基准 / 待逐项落地验收
> 适用范围：全站前端、后端、数据库、编辑器、AI、社区、管理后台、部署与运维

## 1. 项目定位与总体目标

CDPC 是面向 Minecraft 皮肤创作的综合平台，围绕皮肤编辑、服装素材、即时 3D 换装、AI 生成、创作者与社区形成完整创作闭环。

核心目标：
1. 提供可实际使用的皮肤编辑、服装选装、搭配预览和 PNG 导出工具。
2. 支持文生皮肤、图生皮肤及可扩展的 AI 模型接入。
3. 建立素材、作品、创作者和社区内容体系。
4. 提供可靠的用户认证、权限、审核和管理后台。
5. 统一工程架构，降低维护成本，支持持续迭代。

工程原则：
- 全站统一使用 Next.js，不再保留独立 Vite 页面作为正式业务入口。
- 数据库统一使用 PostgreSQL，不再维护 SQLite、MySQL 多数据库适配。
- 采用模块化单体（Modular Monolith），当前阶段不拆微服务。
- 先修复核心工具和真实业务闭环，再扩展非核心功能。
- 复用成熟组件和库，避免重复造轮子。
- 规划状态与代码落地状态必须分开记录；页面存在不等于功能完成。
- 所有重要功能必须有自动化测试或明确的人工验收记录。

## 2. 统一技术栈

### 2.1 前端
| 技术 | 职责 | 采用原则 |
|---|---|---|
| Next.js App Router | 全站框架、路由、服务端渲染 | 唯一正式页面框架 |
| React | UI 组件与交互 | 与 Next.js 配套 |
| TypeScript | 开发语言 | 严格类型检查 |
| Tailwind CSS v4 | 布局、样式与设计 Token 辅助 | 不替代组件库 |
| Mantine | 主要业务 UI 组件库 | 默认优先 |
| shadcn/ui | 补充组件 | 按需使用，不重复建设 |
| Framer Motion | 常规交互动画 | 页面、弹层、轻量反馈 |
| GSAP | 复杂时间轴动画 | 特殊动画按需采用 |
| PWA / Service Worker | 安装能力、缓存与更新 | 独立制定缓存策略 |
| SWC | 编译与转换 | 使用 Next.js 内置集成能力 |

组件库边界：Mantine 作为主要业务组件体系；Tailwind 负责布局和样式；shadcn/ui 仅补足缺失场景。不得在多个组件库中重复维护同类组件。动画库不得同时控制同一个元素。

SWC 是编译工具，不等于 PWA。PWA 还需实现 Web App Manifest、Service Worker、离线策略、版本更新和缓存失效机制。

### 2.2 后端与数据访问
| 技术 | 职责 |
|---|---|
| Next.js Route Handlers | HTTP API |
| Server Actions | 适合的服务端表单和交互 |
| TypeScript / Node.js | 服务端运行与开发 |
| Prisma | ORM 和数据库访问，沿用现有方案并验证版本兼容 |
| Zod | 输入校验与 Schema |
| Auth.js / NextAuth | 认证与 OAuth，沿用现有集成并核实版本 |

复杂业务必须进入模块服务层。页面组件不得直接访问数据库；API 路由不得堆积业务规则；Server Actions 与 Route Handlers 的使用边界必须明确。

### 2.3 3D、像素与图像处理
- Three.js：3D 渲染基础。
- skinview3d：Minecraft 角色与皮肤预览，需核实当前版本、扩展能力和维护状态。
- Canvas：像素编辑、图层合成和图像处理。
- PNG：皮肤及服装素材的主要输入输出格式。
- WebGL：浏览器 3D 渲染能力。
- Framer Motion / GSAP：界面动画，不替代 3D 场景动画系统。

统一角色模型、纹理映射、相机、动作和服装渲染接口，禁止每个业务页面单独维护一套角色渲染器。

### 2.4 基础设施
- Docker：统一容器化与生产运行环境。
- GitHub Actions：CI/CD。
- Zeabur：当前部署平台。
- PostgreSQL：唯一业务关系型数据库。
- S3 兼容对象存储：按需接入，用于 PNG、素材和生成文件。
- CDN：公开图片与素材分发。
- 邮件服务：注册验证、找回和通知。
- AI Provider：模型服务接入。

Redis 暂不作为强制依赖。初期可使用 PostgreSQL 任务表实现可靠的后台任务；当并发、队列吞吐或缓存需求有明确证据时再引入 Redis。

## 3. 总体系统架构

采用模块化单体，逻辑分层如下：
1. 表现层：Next.js 页面、React 组件和交互。
2. API 层：Route Handlers、Server Actions。
3. 业务层：各业务模块的服务与规则。
4. 数据访问层：Prisma Repository / 数据访问封装。
5. 基础设施层：PostgreSQL、对象存储、邮件、AI Provider。
6. 后台任务层：AI 生成、图片处理和其他耗时任务。

模块通过明确的服务接口交互。禁止跨模块随意写表、重复实现业务规则、将权限判断仅放在前端，或让页面直接依赖第三方服务 SDK。

## 4. 业务模块边界

### 4.1 Auth（认证）
邮箱注册、邮箱验证、邮箱登录、密码重置、GitHub / Google / Microsoft / Apple OAuth、会话管理、账号绑定与解绑。

要求：统一登录入口；校验 OAuth state、回调地址和会话；登录失败提供可理解的错误；管理员与普通用户使用统一认证体系并由服务端角色授权。

### 4.2 User（用户）
个人资料、头像、用户名、邮箱、偏好设置、角色状态、作品列表、收藏和使用记录。

### 4.3 Skin（皮肤）
PNG 导入、格式校验、64×64 纹理处理、Classic / Slim 模型识别、预览、编辑、版本管理、撤销恢复和 PNG 导出。

要求：原始皮肤与编辑结果分离；不得静默覆盖用户原文件；导出前验证尺寸、透明通道和纹理兼容性。

### 4.4 Asset（服装素材）
素材分类、上传、详情、预览、作者、授权、版本、收藏、下载、审核和下架。

建议分类至少区分：披肩、帽子、裤子、上衣、外套、鞋子、披风、鞘翅。披肩、外套、披风是不同素材类型，不得混用名称或渲染规则。

素材必须记录作者、归属、授权范围、来源和审核状态。不得把未经授权的官方素材默认作为平台原创素材。

### 4.5 Wardrobe（换装）
导入皮肤、浏览素材、单件穿戴、即时预览、替换与移除、保存搭配、恢复搭配和导出。

交互规则：
- 浏览或选择单件素材时，展示渲染完成的单件素材预览，不强制显示完整人物。
- 用户选择一件服装后，应立即看到角色穿上该素材的效果。
- 用户导入皮肤后，角色预览基于该皮肤实时更新。
- 完整搭配视图展示完整角色。
- 不得要求用户选齐全部素材后才能看到穿戴效果。
- 素材预览、角色穿戴预览和最终 PNG 导出是不同渲染/处理阶段，必须明确区分。

### 4.6 Workbench（创作工作台）
像素编辑、皮肤编辑、服装编辑、图层管理、撤销恢复、3D 预览、资源导入、作品保存和 PNG 导出。

Workbench 复用 Skin、Asset、Wardrobe 和统一渲染服务，不重复建立数据模型。

### 4.7 AI
文生皮肤、图生皮肤、多模型 Provider、模型配置、异步任务、进度状态、失败重试、生成历史、结果保存、额度与成本统计。

任务流程：提交任务 → 服务端校验额度和参数 → 创建任务记录 → 后台执行 → 更新状态 → 返回结果 → 用户编辑或保存。

不得让长时间模型调用依赖单个前台 HTTP 请求一直保持连接。API Key 只能在服务端安全保存和使用。

### 4.8 Creator（创作者）
创作者资料、主页、作品发布、素材发布、作品编辑、作品管理、授权信息和统计。创作者只能管理自己拥有权限的资源。

### 4.9 Community（社区）
公开作品展示、作品详情、评论、回复、点赞、收藏、举报、用户主页和内容审核。社区与创作者中心共享作品数据，不建立重复作品体系。

### 4.10 Admin（管理后台）
用户管理、角色权限、素材管理、作品审核、举报处理、AI Provider 配置、AI 成本统计、平台配置、数据统计、审计日志和系统健康状态。

后台路由可配置，但安全边界必须由服务端权限验证保障。隐藏入口不构成权限控制。

## 5. 路由规划

路由以统一创作工作台和用户空间为准，避免同时维护多套衣橱、工作台和创作者入口。

| 路由 | 职责 |
|---|---|
| `/` | 首页与创作入口 |
| `/ai` | AI 生成入口 |
| `/editor` | 单项皮肤/纹理编辑入口 |
| `/workbench` | 创作入口中心：汇总 AI、单张编辑和 Studio 入口，不承载第二套编辑器状态 |\n| `/studio` | 唯一换装、试穿、搭配和项目工作区，通过 mode/project 参数进入不同工作模式 |
| `/studio?mode=wardrobe` | 换装与衣橱模式 |
| `/studio?mode=edit` | 单件/纹理编辑模式 |
| `/studio?mode=outfit` | 完整搭配模式 |
| `/studio?mode=ai` | 当前项目中的 AI 创作模式 |
| `/u/[username]` | 用户公开主页 |
| `/u/[username]/wardrobe` | 用户公开穿搭 |
| `/u/[username]/creations` | 用户公开作品 |
| `/u/[username]/assets` | 用户公开素材 |
| `/u/[username]/favorites` | 用户收藏，默认仅本人可见 |
| `/u/[username]/settings` | 用户设置，仅本人可访问 |
| `/outfit/[id]` | 穿搭详情 |
| `/asset/[id]` | 素材详情 |
| `/skin/[id]` | 皮肤详情 |
| `/creator` | 创作者中心入口，可兼容重定向至用户创作者空间 |
| `/admin` | 管理后台 |
| `/admin/audit` | 审核管理 |
| `/admin/user` | 用户管理 |
| `/admin/stat` | 数据统计 |

旧的 `/workbench/ai`、`/workbench/edit`、`/workbench/dress` 分别重定向到 `/ai`、`/editor`、`/studio`；`/dress-up` 重定向到 `/studio`；`/wardrobe` 根据当前用户转到 `/u/[username]/wardrobe`。`/workbench` 保留为创作入口中心，不承载编辑器状态；迁移时必须保留必要的 mode、project 和资源 ID 参数，不能维护第二套编辑器或工作台。用户空间使用 `/u/[username]`，不得另行创建 `/@username`、`/profile/[username]` 或重复的个人主页路由。

以上为统一目标路由契约，不代表所有路由已经在当前代码中落地。实际迁移前必须核对仓库路由、深链接、旧路径引用和生产入口。所有正式页面由 Next.js App Router 管理，不保留独立 Vite 页面运行时。

## 6. PostgreSQL 数据模型规划

核心实体建议：

| 实体 | 职责 |
|---|---|
| User | 用户 |
| Account | OAuth 账号 |
| Session | 登录会话 |
| Role / Permission | 角色与权限 |
| Skin / SkinVersion | 皮肤与版本 |
| Asset / AssetVersion | 素材与版本 |
| AssetCategory | 素材分类 |
| Outfit / OutfitItem | 穿搭及组成 |
| Work / WorkVersion | 作品及版本 |
| AIJob | AI 任务 |
| AIProvider | AI 服务配置 |
| AIUsage | AI 使用记录 |
| CreatorProfile | 创作者资料 |
| Comment | 评论 |
| Like | 点赞 |
| Report | 举报 |
| AuditLog | 审计日志 |
| SystemConfig | 系统配置 |
| StoredFile | 文件元数据 |

数据原则：
- 用户、作品、素材具有明确归属。
- 原始皮肤、编辑版本和导出文件分开记录。
- 素材与穿搭通过关联实体建立关系。
- AI 任务与生成结果分离。
- 重要作品和素材保留版本历史。
- 对关键外键、唯一约束和高频查询建立索引。
- 重要的多表写入使用事务。
- 采用有明确规则的软删除和引用检查。
- 所有 Schema 变更通过 Prisma Migration 管理。

数据库是唯一业务数据源。文件二进制不默认存入 PostgreSQL；数据库保存文件元数据、归属、授权和对象存储路径。

## 7. 文件存储与资源处理

目标方案：PostgreSQL 元数据 + S3 兼容对象存储 + CDN。

存储内容：皮肤 PNG、服装 PNG、AI 生成文件、作品预览和缩略图。

上传流程必须包含：身份验证、资源归属校验、文件大小限制、MIME 与真实文件格式验证、图片解码验证、尺寸检查、必要的恶意文件检查和安全存储命名。

私有文件使用受控访问或短期签名 URL；公开素材才允许通过 CDN 公共分发。删除文件前检查数据库引用，避免破坏作品和穿搭。

## 8. UI、响应式与交互规范

- 视觉简洁、专业、功能优先，避免无意义按钮和过度嵌套弹窗。
- 统一颜色、字号、间距、圆角、阴影、层级和交互状态 Token。
- 支持明暗主题。
- 桌面端优先保障编辑器效率，同时保证移动端可用。
- 导航、页脚、用户菜单、通知和错误反馈保持一致。
- 主要操作提供加载、成功、失败和空状态。
- 对编辑操作提供撤销、恢复和未保存提示。
- 减少不必要的页面跳转，保持创作上下文。

Framer Motion 用于常规界面动效；GSAP 用于复杂时间轴和精确控制的特殊动画。动画不得阻塞编辑操作或明显影响 3D 帧率。

## 9. API、代码组织与开发规范

统一要求：
1. 外部输入使用 Zod 校验。
2. API 使用统一响应结构和错误码。
3. 统一分页、排序和筛选参数。
4. 统一日志字段，禁止记录密码、Token 和 API Key。
5. 统一身份验证、角色验证和资源归属检查。
6. 业务逻辑放在模块服务层。
7. 数据访问集中封装，避免页面直接访问数据库。
8. TypeScript 开启严格检查。
9. 环境变量提供 `.env.example` 和文档说明。
10. 新增依赖必须说明必要性、维护状态和运行成本。

## 10. 安全与权限

角色建议：游客、普通用户、创作者、审核员、管理员、超级管理员。

必须实现：
- OAuth state / 回调校验和安全会话管理。
- 密码使用安全哈希算法存储。
- 邮箱验证与密码重置保护。
- 服务端 RBAC 和资源级授权。
- API 限流与滥用防护。
- CSRF、XSS 和注入风险防护。
- 上传文件类型、大小和内容校验。
- AI Provider 密钥服务端安全存储。
- 敏感配置不进入客户端 Bundle。
- 管理员关键操作写入审计日志。
- 用户只能访问自己有权访问的私有数据。

权限判断必须同时考虑用户身份、角色、资源归属和资源当前状态。

## 11. 测试与质量门禁

CI 至少包含：
1. TypeScript 类型检查。
2. ESLint 和格式检查。
3. 单元测试。
4. PostgreSQL 集成测试。
5. 核心 E2E 测试。
6. Next.js 生产构建。
7. Docker 镜像构建与启动检查。

核心 E2E 流程：
- 注册 / 登录 / 退出。
- 导入皮肤并识别模型。
- 编辑并保存皮肤。
- 浏览素材并预览单件素材。
- 选择素材后即时看到角色穿戴效果。
- 保存和恢复完整搭配。
- 导出并验证 PNG。
- 提交 AI 任务、查看状态并保存结果。
- 创作者发布和管理作品。
- 管理员审核内容。
- 普通用户无法执行管理操作。

功能完成标准：代码已合并、测试通过、关键操作真实可用、权限正确、生产构建成功，并有必要的人工验收记录。不能以页面存在、按钮可点击或 PR 描述作为完成依据。

## 12. 部署、监控与恢复

部署链路：GitHub → GitHub Actions → Docker → Zeabur。

要求：
- Next.js 为生产运行入口。
- 生产镜像可重复构建。
- 环境变量在部署平台安全配置。
- 数据库迁移受控执行，避免多个实例同时无序迁移。
- 部署后执行健康检查和关键路由检查。
- 记录镜像版本、Git commit SHA 和部署时间。
- 保留可回滚的稳定镜像。
- 定期备份 PostgreSQL，并实际演练恢复。
- 对服务异常、任务失败和存储错误建立日志与告警。

建议提供基础健康检查与就绪检查端点，例如 `/api/health` 和 `/api/health/ready`。健康检查不得泄露密钥、内部网络信息或完整异常堆栈。

## 13. 国际化与合规

国际化目标：简体中文、英文，预留更多语言。统一翻译字典、日期数字格式、时区和 SEO 元数据。

合规要求：
- 明确 CDPC 与 Mojang、Microsoft、网易等官方主体无关联、不代表官方背书。
- 不暗示获得官方授权。
- 原创素材优先，保存作者、来源和授权信息。
- 建立版权投诉、审核和下架流程。
- 明确 AI 生成内容的使用规则。
- 提供隐私政策、用户协议和社区规范。
- 保护用户上传内容和个人信息。

## 14. 分阶段开发优先级

### P0：基础架构与核心工具
- 全站 Next.js 收敛，移除正式业务中的 Vite 页面入口。
- PostgreSQL 单数据库和迁移流程统一。
- 认证、权限和生产登录修复。
- API、模块边界和工程规范统一。
- UI 设计体系统一。
- 3D 渲染与角色状态统一。
- 皮肤导入、编辑、保存和导出可用。
- 素材管理和即时换装可用。
- Docker 生产部署稳定。

### P1：业务完善
- AI 异步任务和 Provider 管理。
- 创作者中心真实业务流程。
- 社区互动与内容审核。
- 管理后台完整权限和业务流程。
- 对象存储与 CDN。
- 版本管理、审计和国际化。

### P2：体验与商业化
- PWA 离线与更新体验。
- 动效和性能优化。
- 运营统计。
- 会员、付费素材、订单与支付。
- 创作者收益体系。

优先级可根据生产故障和用户反馈调整，但不得以新增功能掩盖 P0 核心工具不可用的问题。

## 15. PR 与项目管理规范

每项开发任务必须说明：
- 需求与验收标准。
- 当前代码实现情况。
- 涉及模块和文件。
- 数据库 Schema / Migration 变化。
- API 和权限影响。
- UI / 交互变化。
- 自动化测试结果。
- 未完成事项和风险。
- 部署及回滚影响。

推荐流程：需求确认 → 仓库现状检查 → 影响分析 → 设计 → 实现 → 测试 → PR 审查 → 合并 → Docker 构建 → 部署验证 → 验收记录。

多个 PR 涉及同一文件或同一业务边界时，先梳理依赖与冲突，避免重复实现和盲目覆盖。合并前检查目标分支最新状态。

## 16. V1.0 执行约束与后续更新

1. 已确定的技术选型不随意变更。
2. 引入新技术必须说明必要性、替代方案、维护成本和部署成本。
3. 不为追求技术新颖增加系统复杂度。
4. 不重复开发已有功能。
5. 不以页面完成代替业务完成。
6. 不以构建成功代替生产验证。
7. 优先解决核心工具不可用、登录失败和数据安全问题。
8. 所有模块共享统一用户、数据库和权限体系。
9. 重大架构变更必须更新本规范并记录原因。
10. 阶段合并后执行回归测试并更新项目状态。

**最终目标：** 建立结构清晰、维护成本可控、可持续扩展的 CDPC 平台，让皮肤编辑、服装换装、AI 生成和创作者生态形成稳定的业务闭环。

> 本文是目标架构和开发规范，不代表所列功能已经在代码中全部实现。实际落地状态必须以仓库代码、自动化测试、部署记录和生产验收为准。
